# Цель работы

Сформировать команду, выбрать веб-приложение для разработки в течение семестра, описать его назначение, пользователей, состав первой версии и правила командной работы.

# 1. Паспорт проекта

| Параметр | Значение |
|---|---|
| Рабочее название | «Видеостудия/продакшн — управление проектами» (кратко: *Studio PM*) |
| Тип приложения | Монолитное веб-приложение (браузер → сервер → БД) |
| Предметная область | Небольшая видеостудия полного цикла: реклама, клипы, корпоративное и событийное видео |
| Проблема | Проекты студии ведутся в мессенджерах, таблицах и на бумаге. Продюсер не видит в одном месте, на каком этапе каждый заказ, кто отвечает за задачу, какие сроки горят и какое оборудование уже занято. Из-за этого срываются дедлайны, одна камера оказывается обещана двум съёмкам, а заказчику сложно ответить, когда будет готов ролик. |
| Назначение | Единая система учёта проектов студии: заказчики, проекты, этапы производства, задачи сотрудников, съёмочная группа и оборудование. |
| Ожидаемый результат | Работающее веб-приложение, в котором продюсер создаёт проект, ведёт его по этапам «препродакшн → съёмка → постпродакшн → согласование → сдан», распределяет задачи и видит прогресс; сотрудники видят свои задачи и меняют их статус. |
| Репозиторий | https://github.com/Nekithogogo/spo |

# 2. Пользователи и предполагаемые функции

**Пользователи (роли):**

- **Продюсер** — принимает заказы, создаёт проекты, назначает съёмочную группу и задачи, контролирует сроки и бюджет.
- **Член съёмочной группы** (режиссёр, оператор, монтажёр) — видит проекты и свои задачи, отмечает выполнение.
- **Администратор студии** — ведёт справочники сотрудников, заказчиков и оборудования, управляет доступом.

**Предполагаемые функции (без формального ТЗ):**

1. Список всех проектов студии со статусом, заказчиком, продюсером и дедлайном.
2. Фильтр проектов по статусу (этапу производства).
3. Создание проекта: название, заказчик, продюсер, тип, бюджет, сроки, описание.
4. Карточка проекта: основные данные, съёмочная группа, задачи.
5. Задачи проекта по этапам производства с исполнителем и сроком.
6. Смена статуса задачи («к выполнению», «в работе», «готово») и отображение прогресса проекта.
7. Перевод проекта по этапам производства.
8. Бронирование оборудования под съёмочные дни без накладок.
9. Справочники сотрудников, заказчиков и оборудования.
10. Вход в систему и права по ролям.

# 3. Состав команды

Проект выполняется одним участником, поэтому по правилам курса все пять ролей совмещены.

| Участник | Роль | Обязанности |
|---|---|---|
| Никита *(ФИО, группа)* | Тимлид | Планирование, распределение задач по неделям, контроль сроков, защита отчётов |
| | Системный аналитик | Сбор и описание требований, сценарии использования, модель данных |
| | Backend-разработчик | Сервер на Flask, REST API, база данных PostgreSQL, развёртывание |
| | Frontend-разработчик | HTML-шаблоны, CSS, JavaScript-логика страниц |
| | Тестировщик | Автотесты API, ручные проверки сценариев, реестр дефектов |

Чтобы совмещение ролей не снижало качество, работа в каждой роли выполняется отдельным шагом: сначала требования (аналитик), затем код (разработчик), затем независимая проверка по чек-листу (тестировщик).

# 4. Границы первой версии (MVP)

**Обязательно к первому показу:**

- список проектов с фильтром по статусу и прогрессом задач;
- создание проекта с проверкой введённых данных на сервере;
- карточка проекта с задачами, сгруппированными по этапам;
- добавление задачи и смена её статуса;
- хранение данных в PostgreSQL, запуск в тестовом окружении (Docker).

**Оставлено на следующие занятия:**

- смена этапа проекта с бизнес-правилами (нельзя сдать проект с незакрытыми задачами);
- бронирование оборудования через интерфейс (таблица в БД закладывается сразу);
- редактирование справочников, управление составом группы;
- аутентификация и роли (ПР №20), безопасность (ПР №22), CI/CD (ПР №27), мониторинг (ПР №28).

# 5. Правила командной работы

| Что | Где и как |
|---|---|
| Исходный код | Git-репозиторий на GitHub: `Nekithogogo/spo`. Основная ветка `main` всегда в рабочем состоянии. |
| Отчёты, диаграммы | В том же репозитории, папка `docs/` (отчёты `docs/reports`, схемы `docs/diagrams`). |
| Задачи | GitHub Issues: одна задача = одна проверяемая единица работы, метка роли (analysis, backend, frontend, test, deploy) и номер практической. |
| Ветки и коммиты | Ветка на задачу (`feature/...`, `fix/...`), осмысленные сообщения коммитов на русском, слияние в `main` после прохождения тестов. |
| Фиксация решений | Важные технические решения записываются в README и в отчёт соответствующей практической (что решили, почему, какие альтернативы). |
| Секреты | Пароли и ключи не попадают в репозиторий: только файл `.env`, шаблон `.env.example`. |
