# Цель работы

Вторая итерация развёртывания ПР №7: укрепить конфигурацию сервера и права доступа, проверить запуск, перезапуск и подключение к БД, защитить секреты и порты, настроить журналы и описать действия при отказе.

# 1. Изменения конфигурации и прав доступа

| № | Изменение | Обоснование |
|---|---|---|
| 1 | Приложение подключается к БД ролью `studio_app` (скрипт `db/03_app_role.sh`) с правами только `SELECT/INSERT/UPDATE/DELETE` | Принцип минимальных привилегий: при уязвимости в приложении нельзя удалить или изменить таблицы |
| 2 | В образе создан системный пользователь `studio` (uid 10001), процесс запускается от него (`USER studio`) | Процесс в контейнере не работает от root |
| 3 | Файловая система контейнера приложения только для чтения (`read_only: true`, `tmpfs: /tmp`), `no-new-privileges` | Злоумышленник не сможет изменить код или установить программы внутри контейнера |
| 4 | Порт БД не публикуется на хост; порт приложения опубликован только на `127.0.0.1` | Доступ к БД только из сети compose, приложение недоступно из внешней сети без прокси |
| 5 | `restart: unless-stopped` для обоих сервисов | Автоматический перезапуск после сбоя процесса или перезагрузки хоста |
| 6 | `healthcheck`: для БД `pg_isready`, для приложения запрос `GET /api/health` (проверяет и БД); `depends_on: condition: service_healthy` | Приложение стартует только после готовности БД, Docker видит реальное состояние сервисов |
| 7 | Ротация журналов: `json-file`, `max-size: 10m`, `max-file: 3` | Журналы не заполнят диск |
| 8 | Часовой пояс БД `Europe/Moscow` | Даты броней и сроков отображаются в местном времени |

Итоговая конфигурация приложения в `docker-compose.yml`:

```yaml
  app:
    build: .
    restart: unless-stopped
    depends_on:
      db:
        condition: service_healthy
    environment:
      DATABASE_URL: postgresql://studio_app:${APP_DB_PASSWORD}@db:5432/${POSTGRES_DB}
      SECRET_KEY: ${SECRET_KEY}
      LOG_LEVEL: ${LOG_LEVEL:-INFO}
    ports:
      - "127.0.0.1:${APP_PORT:-8080}:8000"
    read_only: true
    tmpfs: [/tmp]
    security_opt: ["no-new-privileges:true"]
    logging: *logging
```

# 2. Проверка запуска, перезапуска и подключения к БД

```
$ docker compose ps
NAME        IMAGE                STATUS                    PORTS
spo-app-1   spo-app              Up 20 seconds (healthy)   127.0.0.1:8080->8000/tcp
spo-db-1    postgres:16-alpine   Up 31 seconds (healthy)   5432/tcp
```

| Проверка | Команда | Результат |
|---|---|---|
| Холодный запуск | `docker compose up -d --build` | БД `healthy`, затем приложение `healthy`; `/api/health` → 200 |
| Плановый перезапуск приложения | `docker compose restart app` | через 6 с `/api/health` → 200 |
| Остановка БД | `docker compose stop db` | `/api/health` → 503 «База данных недоступна», приложение не падает |
| Восстановление БД | `docker compose start db` | без перезапуска приложения `/api/health` → 200 |
| Пересоздание контейнеров | `docker compose down && docker compose up -d` | все 5 проектов, включая созданный на стенде, сохранились в томе |
| Аварийное завершение процесса | сигнал SIGTERM процессу gunicorn (PID 1) | контейнер перезапущен автоматически, `RestartCount=1`, `/api/health` → 200 менее чем через 10 с |

# 3. Защита секретов, порты, обновления

**Секреты.** Пароли владельца БД, роли приложения и `SECRET_KEY` хранятся только в файле `.env` на сервере (права `600`). Файл исключён из git (`.gitignore`) и из образа (`.dockerignore`); в репозитории — только `.env.example` с заглушками `change-me-...`. В коде и SQL-скриптах паролей нет: роль `studio_app` получает пароль из переменной `APP_DB_PASSWORD` при инициализации БД.

**Порты.**

| Порт | Где доступен | Назначение |
|---|---|---|
| 8080 | только `127.0.0.1` хоста | веб-приложение |
| 8000 | только внутри сети compose | gunicorn в контейнере |
| 5432 | только внутри сети compose | PostgreSQL (`docker compose port db 5432` — нет публикации) |

На учебной ВМ дополнительно включается брандмауэр: `ufw default deny incoming`, `ufw allow 22/tcp` (SSH для администрирования).

**Обновления.** Версии зависимостей закреплены в `requirements.txt`; базовые образы обновляются пересборкой `docker compose build --pull` раз в неделю или при выходе исправлений безопасности; ОС ВМ — `apt update && apt upgrade`.

**HTTPS.** Стенд доступен только локально (`127.0.0.1`), поэтому HTTPS на этом этапе не требуется. При открытии сетевого доступа перед приложением ставится обратный прокси nginx с сертификатом (Let's Encrypt или учебный), а порт 8080 остаётся закрытым снаружи.

# 4. Журналы и действия при отказе

**Журналы.** gunicorn пишет журнал запросов и ошибок в stdout (настройка `accesslog = "-"`, формат с кодом ответа и временем обработки), приложение — через модуль `logging` с уровнем из `LOG_LEVEL`. Непредвиденные исключения записываются с трассировкой (`log.exception`), а клиенту возвращается только «Внутренняя ошибка сервера». Пароли и тела запросов в журнал не пишутся.

```
$ docker compose logs app --tail 7
app-1 | [2026-10-23 04:47:20 +0000] [1] [INFO] Starting gunicorn 22.0.0
app-1 | [2026-10-23 04:47:20 +0000] [1] [INFO] Listening at: http://0.0.0.0:8000 (1)
app-1 | [2026-10-23 04:47:20 +0000] [7] [INFO] Booting worker with pid: 7
app-1 | [2026-10-23 04:47:20 +0000] [8] [INFO] Booting worker with pid: 8
app-1 | 127.0.0.1 "GET /api/health HTTP/1.1" 200 26 25ms
app-1 | 172.18.0.1 "GET /api/projects HTTP/1.1" 200 2032 19ms
```

При остановленной БД в журнале появляется `ERROR studio.errors: database unavailable: ...`.

**Действия при отказе:**

1. `docker compose ps` — какой сервис не `healthy`.
2. `curl http://127.0.0.1:8080/api/health` — 503 означает проблему с БД, отсутствие ответа — с приложением.
3. `docker compose logs --tail 100 app` / `db` — найти первую ошибку.
4. Отказ БД: `docker compose start db` или `restart db`; приложение восстановит соединения само.
5. Отказ приложения: `docker compose restart app`; если ошибка в новой версии кода — вернуться к предыдущему коммиту (`git checkout <тег>`) и `docker compose up -d --build`.
6. Повторить `./deploy/smoke.sh`.

# Вывод

Тестовое окружение укреплено: приложение работает от непривилегированного пользователя на файловой системе только для чтения и подключается к БД ролью без прав на изменение схемы; БД недоступна с хоста, приложение — только с локального интерфейса; секреты вынесены в `.env`. Настроены проверки состояния, автоматический перезапуск и ротация журналов, описан порядок действий при отказе. Из 13 проверок 12 дали ожидаемый результат, одна (`docker kill`) объяснена особенностью Docker и заменена корректной проверкой.
